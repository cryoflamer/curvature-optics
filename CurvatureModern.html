CPU / WebGPU · optical sample comparison

Frame A is the CPU reference. Use Build CPU replay + GPU frame B to discover the actual adaptive optical-ray requests in A, first build a CPU replay control frame B with the same selected original CPU answers, compare its pixels with A, then batch the identical targets asynchronously on WebGPU and repaint the real physical B frame with GPU-seeded rays and explicit CPU fallback for unsampled/failed rays. This is not a GPU-only frame: painting, adaptive refinement, ground guides and missing rays still use CPU. Requires WebGPU and standard atmosphere; production backend stays unchanged.

GPU-first speed experiment (#140.12.12): the separate Benchmark GPU-first full frame action prepares a distance/height grid from authored objects, computes it asynchronously on WebGPU, and paints a real model B frame without first rendering A or tracing CPU rays to discover targets. A fresh CPU A frame is timed afterwards as an independent cold reference. The grid interpolates GPU data, including visibility classification near boundaries; it is intentionally approximate and must pass real frame comparisons before any production use. The end-to-end GPU number includes preparation, GPU setup/readback and frame painting. The older replay button is retained for controlled diagnostics.

#140.12.15 · fast predictor frame: opt-in WebGPU predictor (RK4 step 500 m), dense scene-derived grid, batched up to 1024 targets at a time. This measures the entire GPU field + real Canvas B frame before a separate cold CPU A reference; compare the actual pixel diff. Approximate grid visibility may create artifacts; no full CPU oracle discovery, no CPU shooting fallback, no production authorization. Larger grids can improve sampling but add work. This is not a CPU-guided adaptive GPU renderer.

#140.12.16 · near-ground grid A/B: the new button compares the original uniform height levels with distance-local ground-focused levels. Both receive the same number of GPU predictor rays and run on one reused WebGPU pipeline (uniform/local/uniform/local). CPU A is rendered independently after the GPU variants. Pixel differences are reported for the whole frame and a fixed lower-left region (left 55%, bottom 45%), now known to be the WRONG side of the user-observed defect (retained for historical A/B reproduction), without treating the region as a certified segmentation. No extra CPU shooting, no production promotion.

#140.12.17 · lower-right GPU grid A/B/C: compares near-ground 256×16, vertical 128×32, and near-distance 256×16, each with exactly 4096 GPU predictor rays (independent of Fast grid selector). All three reuse one GPU pipeline, run in mirrored order A/B/C/C/B/A, and use the same 500 m RK4 step. The pixel difference is measured for the lower-right 45%×45% (correcting the left-side ROI used by #140.12.16) as well as the whole frame. An independent CPU A frame is rendered only after the GPU candidates; no CPU-guided sampling or CPU shooting fallback. B displays the near-distance candidate after measurement, not a CPU-selected winner. No production promotion.

#140.12.18 · adaptive vs dense: a 4096-ray near-distance GPU frame discovers its own uncertain/mixed/rapidly varying optical field queries, then up to 512 exact queried targets are sent to WebGPU and repainted. The control uses a standalone 4608-ray near-distance grid. Both use 500 m RK4, one shared predictor pipeline and no CPU shooting. Adaptive timing includes the entire 4096-ray discovery frame and the second paint. The CPU frame is calculated only after the GPU variants for pixel comparison; the spatial difference maps visualize where significant differences are, not which samples to refine. This is an optional experiment, not a production backend.

#140.12.19 · near-tower geometry diagnostic: reuses a single 4096-ray near-distance GPU predictor grid and paints the same physical scene four times: full refracted GPU field, then analytic no-refraction ray angles and geometric Earth horizon only for targets at or within 1.5, 3, or 6 km. Far targets continue using the GPU field. The analytic path is the existing physical optics vacuum function; it is not a flat-Earth projection. Both fields are sampled for paired-angle and visibility status diagnostics, and the CPU f64 reference is rendered only after all GPU variants. A hard distance boundary may cause seams and is intentional for this experiment; the result is not production-authorized.

#140.12.20 · renderer visibility audit: paints the original 4096-ray GPU B frame unchanged, captures its actual lower-height optical queries within 6 km, samples up to 128 of them across distance bins, then evaluates those identical targets with direct GPU predictor and independent CPU f64 shooting. Reports status disagreements, ground contacts, angular errors and lower-right CPU-frame pixel differences. The sampled queries are low-height renderer queries, not guaranteed to represent uniquely identified tower primitives. The direct GPU and CPU samples are diagnostics only: no results are injected into the picture, no CPU-guided selection or fallback, no production promotion.

#140.12.21 · GPU status qualification: the first 4096-ray grid frame captures its own indeterminate optical requests within 6 km and 20 m height. Two independently selectable diagnostic variants change only those uncertain visibility statuses: a certified direct GPU predictor result (500 m step), and, for still-uncertain direct results, a repeat GPU integration at 50 m. No already-visible or blocked grid status and no original grid angle are changed; unresolved fine-step results stay unresolved. Both enabled also tests their combination. The complete first paint, direct GPU workload, optional fine GPU workload, and every experimental repaint are reported separately; the CPU frame runs last for pixel comparisons. No CPU fallback or production authorization.

#140.12.28 · GPU arithmetic foundation: the independent numerical stand runs the same finite test vectors through separate f32, classic double-single, and integer-residual double-single WGSL pipelines, measuring original f64 input errors and warmed readback-inclusive times. The classic implementation is WGSL-optimizer-sensitive; the integer-residual implementation is a bounded hybrid, not IEEE binary64 or a certified optical solver. It works independently of Globe/Flat and never changes shooting, contact classifications, or painting. Export the JSON for comparison.

#140.12.29 · precision geometry & inputs: an isolated 48-target Globe/Flat coordinate audit compares the actual surfacePoint2-based #140.12.27 normalized f32 atan2 with direct high-precision arc angle d/R and a separate double-single Cartesian atan approximation. It separately compares prepacked absolute coordinates R+h and origin+d with constructing them from independent hi/lo radius, origin, height and distance. This distinguishes input quantization from GPU arithmetic and retains all shooting, contact status and painting unchanged. The polynomial is valid only on the tested small, forward-angle branch; the result is non-certified. Export JSON.

#140.12.30 · Bouguer precision recheck: shoots 48 independent Globe / standard-atmosphere GPU angles once, then uses the unchanged #140.12.27 GPU 256-node log-invariant quadrature as a legacy control and compares three isolated variants: target arc angle from direct f32 d/R, classic double-single d/R and integer-residual double-single d/R. The double-single variants retain the low angle limb in the final ground-contact margin, but do not promote quadrature or atmosphere to double-single. An independent CPU f64 Bouguer quadrature and same-angle RK4 reference run only after the GPU variants. Not a certified visibility test; no shooting, renderer, contact classification or painting changes. Export JSON.

#140.12.31 · GPU Bouguer quadrature precision audit: reuses one independent 48-angle GPU predictor batch on Globe / standard exponential atmosphere. The unmodified #140.12.30 f32 256-node quadrature with double-single d/R is the control. Independent classic and integer-residual double-single GPU variants compute a bounded high-precision log-invariant, refraction profile, integral and ground-contact margin at 128, 256 and 512 midpoint nodes. The fixed-angle CPU f64 128/256/512/2048-node invariant and independent RK4 ground trace are evaluated only after all GPU variants. Polynomial domains are restricted to inward angles and observer heights; outward rays skip ground integration. The default quick audit compiles classic DS only; enable the adjacent checkbox to also compile the slower integer-residual DS for full comparison. Unused arithmetic helpers and branches are excluded from each WGSL program. Quick mode avoids a potentially redundant eager WGSL diagnostics pass (native pipeline creation still validates WGSL); full mode times explicit module diagnostics and pipeline creation. Compilation stages are reported separately, with an elapsed-time indicator. Node counts reuse their respective GPU pipeline. This is neither IEEE f64 nor certified contact/visibility. Shooting, renderer, statuses and painting are unchanged. JSON downloads automatically after success or failure; Export JSON retries the download.

#140.12.32: independent GPU-owned double-single secant angle refinement from the 48 f32 GPU predictor seeds. Two 256/512-node radial Bouguer solves and same-angle DS ground margins are compared with CPU f64 Bouguer and independent CPU RK4 only after both GPU runs. Monotone first-forward radial legs, Globe and standard atmosphere only; targets at observer height or turning branches are out of scope. Margins within 1 cm are uncertain, not certified contact. This is a diagnostic and does not change shooting, visibility, or painting. JSON exports automatically.

#140.12.33: actual-camera sampled pixel-space audit. Runs independent 48-ray GPU DS 256/512 shooting, then CPU f64 roots/RK4, and projects both angle sets using the current Compare A physical camera and its canvas backing-store dimensions. Reports subpixel displacement, changed sampled pixel cells, edge-of-frame and sampled visibility disagreements; ground contacts within 1 cm remain uncertain. These are 48 individual ray samples, not rendered CPU/GPU images or a full-frame pixel diff. A small angular error alone cannot prove a correct horizon/occlusion silhouette. No production rendering changes; JSON downloads automatically.

#140.12.34: real full-frame CPU/GPU predictor pixel parity. Four independent actual Canvas A/B frame pairs (current camera, tilted up/down, narrower field of view) use the same physical Globe/standard scene, 4096 scene-derived GPU f32 predictor samples and separate CPU f64 optics. For each pair the CPU control is cold-painted twice to reject unstable imagery. Full-frame RGB, coverage-vs-white, lower-right and zero-elevation-band differences and contrast-edge proxies are compared at actual backing resolution. Overlaid eye-level/horizon guides are temporarily suppressed. Turn off turbulence; Canvas 2D is required. This GPU renderer path does not use the 48-ray DS shooting shader and is not DS frame parity; neither an edge proxy nor painted/background pixel is certified sky/ground classification. JSON downloads automatically, production remains unchanged.

#140.12.35: algorithmic error attribution (diagnostic only). One shared 4096-ray GPU f32 predictor field is repainted as baseline (nearest-status), conservative strict-status gate (mixed / missing / out-of-grid becomes indeterminate) and strict + up to 192 sparse direct GPU f32 predictor answers chosen from real baseline B renderer queries. All three frames are measured against independent CPU f64 reference at four camera positions. A separate CPU f64 oracle checks exactly the selected GPU query coordinates after the GPU variants. These ablations change recursive geometry paths, so differences are not additive causal percentages. No DS full-frame integration, CPU-guided sample selection, CPU fallback, or production changes. #140.12.36 exports one ZIP with JSON and CPU/GPU/overlay/difference PNGs for all four views.
