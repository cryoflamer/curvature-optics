What is actually being measured?

Each mode processes 1,221 original contours on a 1334 × 889 backing store; the workaround modes replace stroke calls with one fill per outline. Polyline mode uses six segments per contour; other factors do not change the paths, count, color, opacity, or line joins. RAF gaps, JavaScript drawing time, and draw call counts are recorded independently. Modes rotate between passes to reduce order bias. The first 15 RAF callbacks (configurable) of each mode are excluded.

Mode C changes the CanvasRenderingContext2D transform while keeping *effective backing-store line width and path coordinates the same*. It does not change the real display DPR. To compare DPR, repeat a run after changing browser zoom or OS scaling and compare the exported devicePixelRatio values. Mode D uses {willReadFrequently:true} as a context-creation hint; this is not a guarantee of CPU rasterization. For actual backend diagnostics inspect opera://gpu (or chrome://gpu) and browser tracing.

RAF cadence may be limited by display refresh, tab scheduling, thermal state, or browser compositing. Inferred FPS is not the video presentation rate; this tool does not measure GPU work completion. An isolated test that does not reproduce the slowdown does not falsify a Curvature-specific interaction.

F and G compare the native wide stroke(), a single fill() of the union of segment rectangles and internal round joins, and a fast but visibly thinner 1-pixel stroke() control. Each mode keeps the same original polyline, colors, opacity, order, and desired width. Only the rendering method changes. Polygon geometry is rebuilt every frame, so drawMs includes its JavaScript cost.

H isolates the possible CTM-based hairline bypass. For each target width (0.99, 1.005, 1.125, 2.5 backing-store px), the native control uses CTM ×1 and lineWidth = target; the unit-width variant uses CTM ×target and lineWidth = 1; the half-width variant uses CTM ×(2 × target) and lineWidth = 0.5. Coordinates are divided by the exact CTM scale. All three should paint the same physical line geometry. H explicitly tests whether the renderer uses the assigned width or the transformed width to select its fast path; merely changing lineWidth does not guarantee a bypass. Unlike real DPR changes, this is an internal Canvas transform only.

I measures a new WebGL2 renderer: a single instanced draw call paints all 1,221 polyline strokes using an analytic screen-space signed-distance outline (butt caps and round internal joins). Each polyline is composited once, avoiding double opacity at translucent joins. The cached mode uploads geometry once; the streaming mode rebuilds the vertex buffer in JavaScript and reuploads it every frame, simulating changing camera geometry. Unlike a native stroke(), this is a custom approximate antialiasing implementation.

J renders the background, 1,189 path fills, and 1,221 strokes entirely with WebGL2. A fill-then-stroke fragment is composed for each path instance, preserving per-path painter ordering (including overlaps with later fills), rather than incorrectly putting all lines above all fills. This is an isolated proof of rasterization, not yet a Canvas2D/WebGL2 production hybrid. A production split must preserve ordering separately. WebGL2 may use hardware or software drivers; no browser GPU backend is assumed. No readPixels() occurs during sampled frames.

The pixel comparison below runs after the RAF benchmark and is never included in timing. It compares composited RGB pixels (with a background-aware mask), not vector geometry. Differences may remain from antialiasing even if the shapes are geometrically equivalent. No browser GPU-completion timing is claimed.
